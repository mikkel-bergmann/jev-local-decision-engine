## ADDED Requirements

### Requirement: A binary gate decides whether a query is a tool request
id: tool-request-gate

The system SHALL provide a binary head over the same frozen shared features that answers whether a
query is a tool request, adding no encoder forward pass beyond the one a decision already costs. The
gate SHALL be trained on hand-authored examples only, never on labels from the constrained engine,
taking the existing tool-routing queries as positives and authored non-requests as negatives.

#### Scenario: The gate accepts a tool request
- **WHEN** the gate scores a query that asks for an action in the catalogue, such as refunding a
  charge or booking an inspection
- **THEN** it reports the query as a tool request

#### Scenario: The gate rejects conversation and out-of-domain text
- **WHEN** the gate scores text that asks for no catalogue action, such as a greeting, an arithmetic
  question, or a request for a poem
- **THEN** it reports the query as not a tool request

#### Scenario: The gate costs no extra encoder pass
- **WHEN** a query is scored by both the gate and the tool head
- **THEN** exactly one encoder forward pass executes

### Requirement: Gate negatives are authored and varied
id: gate-training-data

The system SHALL carry at least one hundred and fifty hand-authored negative examples spanning
greetings, questions with no action, statements, opinions, out-of-domain requests, and incomplete or
ambiguous fragments. Negatives SHALL NOT be generated by templating a small set of frames.

#### Scenario: Negatives are numerous and varied
- **WHEN** the gate's negative training data is loaded
- **THEN** it holds at least one hundred and fifty items, and no fixed phrase of four or more words
  appears in more than one tenth of them

#### Scenario: Positives come from the tool queries
- **WHEN** the gate's training data is assembled
- **THEN** its positives are the hand-authored tool-routing queries, and no label is read from the
  constrained engine

### Requirement: The decision threshold is measured, not chosen
id: gate-threshold

The system SHALL select the gate's decision threshold by sweeping candidate values against a
holdout and recording the measured precision, recall, and negative-rejection rate at the chosen
value. The selected number SHALL appear in the code with a comment naming the measurement that
produced it. The system SHALL NOT ship a threshold chosen by judgement alone.

#### Scenario: The sweep reports both directions of the trade
- **WHEN** the threshold sweep runs
- **THEN** it reports, for each candidate, the share of negatives rejected and the share of genuine
  tool requests retained

#### Scenario: The shipped threshold traces to a measurement
- **WHEN** the selected threshold is read from the code
- **THEN** it carries the precision, recall, and negative-rejection rate measured at that value

### Requirement: Routing abstains when the gate rejects
id: gated-routing

The system SHALL provide a routing entry point that consults the gate before the tool head and
returns no tool when the gate rejects the query. It SHALL report the gate's probability alongside
its verdict so a caller can apply its own policy. The system SHALL NOT alter `run_heads_decision`,
whose `decision` field remains a string for every field it returns.

#### Scenario: A rejected query yields no tool
- **WHEN** the routing entry point scores text the gate rejects
- **THEN** it reports the query as not a tool request, returns no tool name, and returns an empty
  shortlist

#### Scenario: An accepted query routes as before
- **WHEN** the routing entry point scores text the gate accepts
- **THEN** it returns a catalogue tool name and a shortlist, matching what the tool head alone would
  return for that text

#### Scenario: The gate probability is always reported
- **WHEN** the routing entry point scores any text
- **THEN** the result carries the gate's probability, whether the verdict was accept or reject

### Requirement: Gate evaluation uses a late-authored holdout
id: gate-evaluation

The system SHALL evaluate the gate on a holdout authored after its training data, disjoint from it,
and checked for paraphrase overlap rather than only exact-text overlap. Any fold split SHALL shuffle
with a seeded generator before partitioning. The report SHALL name both the negative-rejection rate
and the share of genuine requests retained.

#### Scenario: The holdout is disjoint from training
- **WHEN** the gate holdout is compared against the gate's training data
- **THEN** no item text appears in both

#### Scenario: Fold splits are shuffled
- **WHEN** any cross-validation partitions the gate data
- **THEN** it shuffles with a seeded generator first, rather than striding across an ordered list

#### Scenario: The report names both directions
- **WHEN** gate evaluation runs
- **THEN** it reports the share of negatives rejected and the share of genuine tool requests
  retained, not an aggregate accuracy alone

### Requirement: The inspection queries join the tool training data
id: inspection-training-data

The system SHALL include the twenty hand-authored inspection queries in the tool head's training
data, covering the audit checklist, inspection scheduling, inspection reporting, violation logging,
and audit scheduling tools.

#### Scenario: The inspection queries are loaded for training
- **WHEN** the tool training data is loaded
- **THEN** it includes the inspection queries, and every tool named by them has at least four
  training queries
